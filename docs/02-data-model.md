# 02 — Data model (Neon Postgres)

**Source of truth:** `lib/db/schema.ts`. This document explains it. If they
disagree, the schema file is right and this document must be fixed.

Migrations live in `drizzle/` (generated by `drizzle-kit generate`,
committed). The first migration is `drizzle/0000_init.sql` (22 tables).

## 1. Design principles

1. **One row per real thing.** A sūtra is one row; a verse is one row; a
   note is one row. No "blob of a whole chapter."
2. **Text stays exactly as typed.** Sūtra numbers and verse numbers are
   `text` (`"0.1.3"`, `"16-18"`). Transliteration is never auto-generated.
3. **Ordering is explicit.** Every list has a `position` or `sort` integer.
   Import assigns 10, 20, 30… so the admin can insert between rows without
   renumbering.
4. **Enum-like columns are `text`**, typed in TypeScript
   (`text("status", { enum: [...] })`), not Postgres `ENUM` types — adding a
   value never needs a migration. zod enforces the allowed values on write.
5. **Custom fields go in `extra jsonb`**, keyed by `field_definitions.key`.
   The definition table gives label, order, language (Sanskrit/English),
   and whether it's rich text. This is how "any extra column auto-appears."
6. **Every content row has** `status` (`draft | published | archived`),
   `created_at`, `updated_at`, and `updated_by`. Public reads only ever see
   `status = 'published'`.
7. **Every write is recorded** in `revisions` (before/after JSON) so any
   edit can be inspected and undone.
8. **Additive evolution.** New columns are nullable or have defaults; we
   never drop or rename a column in the same release that stops using it
   (`13-engineering-standards.md` §6).

## 2. Entity map

```
editions 1─* chapters 1─* subchapters
                │              │
                └──────* sutras *┘ (subchapter optional)
                          │ 1─0..1 sutra_notes
books 1─* cantos (SB only)
books 1─* scripture_chapters 1─* verses
(sutras | verses | chapters | scripture_chapters | daily_items)
      1─* audio_links         (polymorphic: entity_type + entity_id)
      1─* script_overrides    (polymorphic)
chapters 1─* practice_topics 1─* practice_questions
field_definitions  → describe keys inside sutras.extra / verses.extra
home_blocks, daily_items, daily_pins, posts, site_settings
admin_users 1─* revisions, login_attempts
```

Polymorphic tables (`audio_links`, `script_overrides`, `daily_pins`) can't
have a database foreign key. Their integrity is enforced in code: the
server action that deletes a sūtra/verse also deletes its audio links and
overrides in the same `db.batch()`.

## 3. Tables

### 3.1 HNV

**`editions`** — `madhyama` (published), `laghu`, `brhat` (unpublished
until they have content). `slug` unique.

**`chapters`** — one per prakaraṇa per edition. Unique `(edition_id, slug)`.
`number` is the displayed chapter number (null for Maṅgalācaraṇa and
Afterword). `kind` is `sutras` or `verses`. `range_label` is display text
("1–86").

**`subchapters`** — named groups inside a chapter, in `sort` order. Unique
`(chapter_id, slug)`. Slugs are generated from titles (`slugify`) at import.

**`sutras`**

| Column | Notes |
|---|---|
| `number` | Text, unique per edition: `"1"`…`"1278"`, `"0.1.1"` (Maṅgalācaraṇa), `"0.2.1"` (Afterword). Used in URLs `/chapters/<slug>/<number>` and anchors `#<number>`. |
| `position` | Order inside the chapter. |
| `sanskrit`, `transliteration`, `synonyms`, `vrtti`, `translation` | Plain text; `/` = line break. Empty string = "not yet entered". |
| `extra` | `{ [fieldKey]: string }` for custom fields. |
| `daily_eligible` | In the Verse of the Day pool. |

Indexes: `(edition_id, number)` unique; `(chapter_id, position)`.

**`sutra_notes`** — at most one per sūtra (`sutra_id` is the primary key).
`html` is sanitized on write. `source` records `gdoc-import` vs `admin`.

### 3.2 Scriptures

**`books`** — `code` is lowercase (`sb`, `bg`) and is the URL segment.
`structure` = `canto_chapter_verse` (SB) or `chapter_verse` (BG).

**`cantos`** — SB's 12 cantos with `expected_chapters` (19, 10, 33, 31, 26,
19, 15, 24, 24, 90, 31, 13 = 335).

**`scripture_chapters`** — unique `(book_id, canto, number)`. For BG,
`canto = 0` (a real value, not NULL, so the unique index works).

**`verses`**

| Column | Notes |
|---|---|
| `canto`, `chapter` | Denormalised copies for URL lookup (`canto = 0` for BG). |
| `verse_key` | Last URL segment, exactly: `"1"`, `"16-18"`. |
| `verse_no` | Full display number: `"1.12.1"`, `"18.6"`, `"1.16-18"`. |
| `verse_from`, `verse_to` | Integers covered by the row (`16`,`18`). Lets `/sb/1/1/17` find `16-18`. |
| `iast`, `devanagari` | Verse text; `/` = line break. |
| `extra` | Custom fields: `anvaya`, `translation`, `word_for_word`, `commentary`, … |

Unique `(book_id, canto, chapter, verse_key)`; index on
`(book_id, canto, chapter, verse_from, verse_to)` for range lookups.

**Translation is a custom field**, not a fixed column, because v6 says
everything beyond number/IAST/Devanagari is an "extra column." Phase 1
seeds these `field_definitions`:

| scope | book_code | key | label | language | is_commentary | sort |
|---|---|---|---|---|---|---|
| verse | null | `anvaya` | Anvaya | sanskrit | true | 10 |
| verse | null | `translation` | English Translation | english | true | 20 |

Sūtras use fixed columns for synonyms/vṛtti/translation (they are defined
by v6 §5.3) and `extra` only for additional fields.

### 3.3 Cross-cutting

**`field_definitions`** — unique `(scope, coalesce(book_code,''), key)`.
`key` is `snake_case`, immutable once data exists (renaming the *label* is
always safe; renaming the *key* needs a data migration).

**`script_overrides`** — hand-written text for one field in one script,
e.g. the Bengali rendering of sūtra 42's Sanskrit. Unique
`(entity_type, entity_id, field_key, script)`. The script engine prefers an
override over automatic conversion (`07-script-engine.md`).

**`audio_links`** — `title`, `speaker` (free text), `url`, `sort`. Links
only.

### 3.4 Home & daily

**`home_blocks`** — `kind` selects the renderer; `config jsonb` holds
renderer-specific options; `sort`, `is_visible`.

**`daily_items`** — Subhāṣita entries (`pool = 'subhashita'`).

**Verse of the Day** has no table of its own: the pool is every
published sūtra/verse with `daily_eligible = true`.

**`daily_pins`** — `(pool, date)` unique; points to the item to show on that
date.

### 3.5 Practice

**`practice_topics`** — per chapter, with an optional sūtra range. Seed for
Saṁjñā-sandhi-prakaraṇa:

| slug | title | sutra_from–to |
|---|---|---|
| `vowel-sandhi` | Sarveśvara-sandhi | 41–60 |
| `consonant-sandhi` | Viṣṇujana-sandhi | 61–78 |
| `visarga-sandhi` | Viṣṇusarga-sandhi | 79–86 |

(Saṁjñā 1–40 gets its own topic when terminology questions are written.)

**`practice_questions`** — `code` is the stable human id (`v1`, `c3`, `s11`),
`options jsonb string[]`, `correct_index`, `explanation`,
`sutra_refs text[]` (must be non-empty — enforced by zod).

### 3.6 Admin & history

**`admin_users`** — email unique case-insensitively
(`lower(email)` index); `password_hash` (bcrypt, cost 12); `role`;
`session_version` (bump to log a user out everywhere).

**`login_attempts`** — for rate limiting (5 failures / 15 min / email → 15
min lockout).

**`revisions`** — `entity_table`, `entity_id`, `action`, `before`, `after`,
`user_id`, `note`. Written in the same `db.batch()` as the change itself.

**`site_settings`** — key/value JSON for small global settings (e.g. default
script, maintenance banner).

## 4. Invariants (checked by `scripts/verify-db.ts`)

1. Every `sutras.chapter_id` belongs to the same `edition_id` as the sūtra.
2. A `sutras.subchapter_id`, when set, belongs to the sūtra's chapter.
3. Every `verses.chapter_id` row has the same `book_id`, `canto`, and
   `chapter` as the verse.
4. `verse_from <= verse_to`; `verse_key` matches `^\d+(-\d+)?$`.
5. Every `extra` key exists in `field_definitions` for that scope/book.
6. Every `practice_questions.sutra_refs` value exists as a sūtra number.
7. `correct_index` is a valid index into `options`; options are distinct.
8. Imported counts equal source counts (`03-content-pipeline.md` §2.4).

The script prints every violation and exits non-zero. It runs after every
import and in CI against the `dev` branch.

## 5. Common queries (patterns, not exact code)

```ts
// Chapter page: chapter + subchapters + published sūtras + note flags
const ch = await db.query.chapters.findFirst({
  where: (c, { and, eq }) => and(eq(c.editionId, edId), eq(c.slug, slug), eq(c.status, "published")),
});
const rows = await db
  .select({ s: sutras, hasNote: sql<boolean>`${sutraNotes.sutraId} is not null` })
  .from(sutras)
  .leftJoin(sutraNotes, and(eq(sutraNotes.sutraId, sutras.id), eq(sutraNotes.status, "published")))
  .where(and(eq(sutras.chapterId, ch.id), eq(sutras.status, "published")))
  .orderBy(sutras.position);

// Verse by URL, including "17" → "16-18"
const v = await db.select().from(verses).where(and(
  eq(verses.bookId, book.id), eq(verses.canto, canto), eq(verses.chapter, chapter),
  or(eq(verses.verseKey, key), and(lte(verses.verseFrom, n), gte(verses.verseTo, n))),
)).limit(1);
```

Never `select *` across a whole book in a request path. The largest
legitimate read is one chapter's verses (BG 18 has 78; SB 10.90 has 50) or
one HNV chapter's sūtras (Ākhyāta: 359).

## 6. Size estimate

| Content | Rows | Approx. size |
|---|---|---|
| Sūtras (Madhyama) | 1,290 | < 5 MB with vṛtti & translation |
| SB verses | ~18,000 | ~60–90 MB with anvaya & translation |
| BG verses | ~700 | ~3 MB |
| Notes, revisions, misc | — | grows; revisions pruned to 50 per entity |

Neon Free gives ~0.5–1 GB per branch (`branch_logical_size_limit` reported
for this project: 1 GiB). Comfortable for years; monitor in
`14-operations.md` §6.
