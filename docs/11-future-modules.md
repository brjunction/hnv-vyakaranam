# 11 — Future modules (all in scope, sequenced in `12-roadmap.md`)

Each module below has: goal, design, data, and done-criteria. None of them
may break an earlier module's URLs or rules.

## 1. Site-wide search (Phase 8)

**Goal:** one search box finds sūtras, verses, notes, posts, and wiki
pages by Sanskrit (Devanagari or IAST, with or without diacritics) or
English.

**Design:** Postgres full-text search in Neon (native, no extra service).

- Migration adds extensions `unaccent` and `pg_trgm`, and a
  `search_documents` table: `(id, entity_type, entity_id, url, title,
  snippet_source, lang, tsv tsvector, plain text)`.
- `tsv` = `to_tsvector('simple', unaccent(<IAST + translation + vṛtti +
  notes text>))`, GIN-indexed; `plain` gets a trigram GIN index for fuzzy
  matching (`kṛṣṇa` ≈ `krsna` ≈ `krishna`).
- Devanagari queries are converted to IAST with sanscript before matching.
- Rows are refreshed by the same server actions that edit content (inside
  the same `db.batch`) and fully rebuilt by `scripts/db/reindex-search.ts`.
- `/search?q=` is a dynamic page; the query API
  (`/api/search?q=&type=`) responds with `Cache-Control: public,
  s-maxage=86400, stale-while-revalidate=604800` so repeated queries are
  served by the CDN. **This is the one documented exception** to "visitors
  never wait on the database" — a search is inherently a query.
- Results grouped by type, 10 per group, highlighted with `ts_headline`.
- Header gets a search icon (⌘K / Ctrl+K opens a command palette).

**Done when:** "rāmaḥ", "रामः", "ramah", and "visarga" each return the
expected sūtras within 300 ms (warm) and the page is fully keyboard usable.

## 2. Wiki (Phase 8)

**Goal:** the self-contained `public/hnv-wiki.html` (≈370 kB, 4,631 lines)
becomes editable, linkable pages.

- `wiki_pages (id, slug unique, title, body_html, parent_id, sort, status,
  timestamps)` + revisions (generic `revisions` table).
- One-time import: split the HTML file by its top-level section headings
  into pages, keep anchors, rewrite internal links.
- `/wiki` (index tree) and `/wiki/[...slug]` (static, ISR via tag `wiki`).
- `/hnv-wiki`, `/HNV-Wiki`, `/hnvwiki` → 308 → `/wiki` (keep the old static
  file reachable at `/hnv-wiki.html` until the import is verified, then
  remove).
- Auto-links: `Sūtra 42` text in wiki pages links to the sūtra page
  (rendered at build, not stored).

## 3. Reader accounts: My Notes, bookmarks, history, settings (Phase 9)

**Goal:** optional sign-in for readers. The site stays fully usable
without an account.

- Auth: decide at phase start between **Neon Auth** (managed, lives in the
  same Neon project) and **Better Auth** (library, tables in our schema).
  Requirements either way: Google sign-in + email magic link, no
  passwords for readers. Record the choice in `DECISIONS.md`.
- Admin auth stays separate (`04-admin.md`); a reader account never gets
  admin rights.
- Tables (added by their own migration):
  - `readers (id, email, name, created_at, …)` (or the auth provider's)
  - `reader_notes (id, reader_id, entity_type, entity_id, body, created_at, updated_at)`
  - `bookmarks (reader_id, entity_type, entity_id, created_at)` PK on all three keys except time
  - `reading_history (reader_id, entity_type, entity_id, last_read_at)` — upsert, keep last 500
  - `reader_settings (reader_id PK, script, theme, notes_visible, font_scale)`
- All reader features work **logged-out first** with `localStorage`
  (`hnv:bookmarks:v1`, `hnv:history:v1`, `hnv:mynotes:v1`), then sync on
  sign-in (merge, newest wins per item).
- Reading pages stay static: personal data is fetched client-side from
  `/api/me/*` (dynamic, `Cache-Control: private, no-store`).
- Privacy page; "Delete my account" removes all reader rows.

## 4. Grammar tools (Phase 10)

| Tool | What it does | Notes |
|---|---|---|
| Sandhi joiner | two words → joined form + which sūtra(s) fired | Rule engine in `lib/grammar/sandhi/*`, each rule a pure function tagged with its sūtra number; unit tests from the verified practice bank |
| Sandhi splitter | joined form → candidate splits (ranked) | Built on the joiner run backwards; shows all candidates, never claims certainty |
| Declension tables | stem + gender → all forms | Data-driven paradigm tables entered in the admin (`paradigms` table), not hand-coded |
| Conjugation tables | root + gaṇa + lakāra → forms | Same approach |
| Dhātupāṭha | browse roots with meaning and gaṇa | `dhatus` table, admin-managed |

Rule: any tool output that is generated (not entered) is labelled
"Generated by rule — verify against the text," with the sūtra numbers it
used. This is how tools stay compatible with "never invent content."

## 5. PWA & offline (Phase 10)

- Web app manifest, icons (from `hnvlogo.png`, resized to 192/512, ≤ 30 kB
  each), theme color.
- Service worker (Serwist): cache-first for static assets; stale-while-
  revalidate for reading pages; "Download this chapter / canto for offline"
  button that pre-caches its pages.
- Admin is never cached by the service worker.

## 6. Laghu & Bṛhat editions (Phase 10)

- Content entered through the admin or imported from XLSX into their own
  `edition` rows.
- URLs `/laghu/chapters/...`, `/brhat/chapters/...`; Madhyama stays at
  `/chapters`.
- Edition comparison view (same sūtra across editions) only if numbering
  correspondence is defined (open question in `00-requirements.md` §13.1).

## 7. More scriptures (only if requirements change)

The schema supports any number of `books`. Adding one = a requirements
update, then: insert `books` row (+ `cantos` if needed), import verses,
add sitemap file. No code changes to the reader.
